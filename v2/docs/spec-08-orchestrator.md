# Spec: Orchestrator & Web Service

## Overview
The Orchestrator & Web Service feature is the final piece of the v2 atomic streaming architecture. It coordinates the entire pipeline, manages the lifecycle of all workers, and provides the web service interface for serving results, logs, and proxy functionality.

## Requirements
1. **Orchestrator**:
   - Manages the lifecycle of all workers (Discovery, Validation, Scan Workers, Scoring, Result Writer, Proxy Worker if applicable).
   - Starts and stops workers in the correct order.
   - Handles the flow of events between workers via the EventBus.
   - Provides a way to start a scan job with a given scan mode (Fast, Full, Deep).
   - Monitors the progress of the scan and emits progress events.
   - Handles errors and graceful shutdown.
   - Can be run as a one-time scan or as a scheduled task (using the existing scheduling mechanism from the original codebase).

2. **Web Service**:
   - Serves the result files (txt, m3u, ipv4/ipv6, hls) generated by the Result Writer.
   - Serves log files (result.log, speed_test.log, statistic.log, etc.).
   - Serves the proxy endpoint (if enabled) using the ProxyWorker.
   - Serves the update-status endpoint for real-time progress monitoring.
   - Serves other existing endpoints (e.g., /logo/, /epg/, etc.) by serving static files or proxying to the original service if needed.
   - Can be run with a production server (e.g., gunicorn) or a development server.
   - Should be able to run in the background while the orchestrator is running (or we can run the orchestrator within the web service process? ## Technical Specifications
- Orchestrator:
   - Receives a ScanJobStartedEvent (or we can have a method to start a scan job).
   - Creates and starts all workers in the correct order:
      1. Discovery Worker
      2. Validation Worker
      3. Scan Workers (FastScanWorker, FullScanWorker, DeepScanWorker) - we can start all scan workers in parallel, or we can start them sequentially based on the scan mode? Actually, we want to run the pipeline in the order: Discovery -> Validation -> Scanning -> Scoring -> Result Writing. The scanning workers can be started after validation, and they can run in parallel (each listening to the EventBus for validated URLs).
      4. Scoring Worker
      5. Result Writer
      6. Progress Reporter
   - Waits for the scan to complete (we can wait for a ScanJobCompletedEvent from the Result Worker or from the Orchestrator itself after all workers have finished).
   - Handles errors and graceful shutdown.
   - Can be configured to run in one-time mode or continuous mode (using the existing scheduler configuration).

- Progress Reporter:
   - Listens to all events (or a subset of events) from the EventBus.
   - Updates the processing_status singleton with the current phase, progress, current URL, etc.
   - We can map events to phases:
      * DiscoveryWorker events -> phase: "discovery"
      * ValidationWorker events -> phase: "validation"
      * ScanWorker events -> phase: "scanning" (with sub-mode: fast, full, deep)
      * ScoringWorker events -> phase: "scoring"
      * ResultWriter events -> phase: "result_writing"
   - We can also emit a ScanJobProgressEvent periodically (or we can rely on the Progress Reporter to update the processing_status singleton).

   - The processing_status singleton already has a set_phase method that we can call.

- We will need to extend the EventBus to allow broadcasting events to all workers (which it already does).

- We will need to ensure that all workers are properly started and stopped.

- We will need to handle the configuration for the orchestrator (e.g., scan mode, whether to run continuously, etc.) from config.ini.

## Event Types
- Consumes: ScanJobStartedEvent (to start a scan job)
- May emit: ScanJobCompletedEvent, ScanJobFailedEvent, ScanJobProgressEvent (for progress reporting)
